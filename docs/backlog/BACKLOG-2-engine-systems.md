## Standing Directive — Code Comments (user directive 2026-08-23)

> **Binding on every increment in this file.** Where this and a §-row's own instructions disagree, this wins.

**The failure this prevents:** writing a comment that narrates the change being made right now. That context is real, but it expires the instant the change merges — the defect it describes no longer exists, so the comment becomes a story about a problem no future reader can observe. It is a changelog entry in the wrong file, and a third copy of text already required in the commit body and the PR description.

- **CC-1 (MUST NOT)** Write a comment describing a change, a fix, a defect, its cause, or what the code used to do. No *"was / now / previously / instead of"*, no *"this fixes"*, no *"needed because otherwise"*, no *"note that we no longer"*.
- **CC-2 (MUST)** Apply the **survival test** to every comment before writing it: *would this still be true and useful to someone reading this file a year from now, who never saw the diff?* If it only makes sense beside the diff, it is changelog — delete it and put it in the commit body.
- **CC-3 (MUST)** Default to **zero** comments. Declarative config — Terraform, DNS records, k8s manifests, CI YAML, Helm values — is self-describing and takes none. A resource named `dmarc-example-com` does not need a comment saying it is the DMARC record.
- **CC-4 (MAY)** Comment only when a future editor would actively break something without it: a non-obvious external constraint, a required out-of-band manual step, an invariant the surrounding code cannot show. **One line.** If it needs a paragraph it belongs in a design doc, not inline.
- **CC-5 (MUST)** Before every commit, re-read the comment lines added: `git diff --cached | grep '^+' | grep -E '#|//|/\*'`. Each hit must pass CC-2 on its own. **Deleting is always an acceptable outcome.** *"I already wrote it"*, *"it is only one line"*, and *"this one is genuinely useful"* are not exemptions — the last one is the exact thought that precedes every violation.
- **CC-6 (MUST)** Applies to comments **edited** as well as added. When a change invalidates an existing comment, the default action is **DELETE**, not rewrite it into a new narrative.

> **⚠️ KNOWN TENSION, flagged not resolved — needs a user call.** This repo currently runs an *opposite* convention in `play.html`: **§AUDIT-03n / §DX-02c "annotate, don't rewrite"**, which deliberately preserves defect history inline (e.g. `const NODE_NPC_KEYS`'s 8-line comment explaining that 21 of 26 rows named retired node codes, or `_renderFinalMap`'s §AUDIT-03e note on why the node filter is held at the historical set). Those are exactly the *"what the code used to do"* narratives CC-1 forbids, and several are load-bearing: they are the only record of why a value is held where it is, and deleting them would re-open closed audit rows. **Until the call is made, the working rule is:** CC-1..CC-6 bind all **new** comments; existing §AUDIT-/§DX-annotated blocks are **not** swept under CC-6 — they are a documented archaeology convention, not accidental changelog. ### §OFFHAND-01 — the off-hand bonus action is not the dagger you equipped, and it is not gated on equipping one (NEW 2026-08-26 during §WEAP-FIN-FU, 🟠 design call)

- [ ] **§OFFHAND-01 — `S.offhand` has two writers and both are dice-roller UI handlers.** `S.offhand.count  = parseInt@8049` and `setupDieSelector('offhand-die-sel'@8367`. **Nothing in the story layer ever writes it.** So `_overlayOffhandAttack` — a live bonus action on the story battle overlay — rolls the initial-state literal `offhand: { die: 4, count: 1, shield: false }@5304` forever, and `const hasOffhand = S.offhand && S.offhand.count > 0@24809` is therefore **always true**: the 🗡 Offhand button is shown and enabled in every story battle, for every character, whether or not a dagger is equipped (the only disabler is `shielded`).
> **Three separate things are wrong and they need deciding together.** (1) **The equipped dagger does not arm the off-hand.** `S_story.equippedWeapon` is the dagger slot, and what it actually does is add `atkBonus` to the **main-hand** roll (`S_story.equippedWeapon.atkBonus@25052`) — so the dagger you equip helps your sword, and the off-hand attack you always have is unrelated to it. (2) **`DAGGER_ITEMS` carry no `die` at all** — they are `atkBonus` accessories, not weapons — so there is nothing for an off-hand die to be synced *from*. The d4 is a literal, not a derivation. (3) **The off-hand cannot express its own attack ability**, which is what §WEAP-FIN-FU(a) was filed to fix: `_overlayOffhandAttack` calls the shared `getAtkAbilityMod()`, so a rapier in the main hand already makes the off-hand DEX-keyed and a maul already makes it STR-keyed.
> **(a) of §WEAP-FIN-FU is BLOCKED behind this row, and that is why it did not ship with (b).** Giving `DAGGER_ITEMS` a `finesse` field answers a question nothing asks: the off-hand is not the equipped dagger, so per-hand finesse would be a property of a weapon that never reaches the roll. **Fix the identity first, then the ability.**
> **The design call is what the off-hand IS.** (i) **An always-available knife** — the current behaviour, made deliberate: gate nothing, document the d4 as innate, and drop the dagger-slot confusion by renaming. (ii) **The equipped dagger** — sync `S.offhand` from `S_story.equippedWeapon`, gate `hasOffhand` on it, and give `DAGGER_ITEMS` a die; this is the reading the UI's own 🗡 icon and the slot's name imply, and it makes the four magic daggers matter as weapons rather than as flat bonuses. (iii) **Leave it.** **Recommend (ii)**, but it is 🟠 rather than 🟡 because it changes the action economy of every existing character — a player who has never equipped a dagger loses a bonus action they have had all game — and because §FISH-02 already records that **no live path grants any of the four magic daggers**, so (ii) ships a slot the player cannot fill until that row moves.
> **Do NOT sweep this into a weapon-property row.** It is an action-economy and item-identity question, and the three sub-findings above are only visible together.
> **Measure the blast radius before answering.** Option (ii) takes a bonus action away from every character that has never equipped a dagger, so the count that decides it is: how many existing saves carry no `S_story.equippedWeapon`, and whether any quest, encounter or balance note assumes the off-hand swing exists. Neither number has been taken.
> **Provenance:** §WEAP-FIN-FU, whose half (a) was disproved by grepping for the writers of the thing it proposed to give a field to. The blast-radius clause is item (i) of the §NEXT-2026-08-26 hand-off.

### §WAVE-01 — a node battle is one monster, and three labels promise a sequence (NEW 2026-08-24 during §DX-02gv, 🟠 design call)

- [ ] **§WAVE-01 — the battle path has no concept of a wave.** **Measured during §DX-02gv:** `storyCommitBattle@36606` resolves one opponent (`MONSTER_POOL[node.battle.key] || EPIC_BOSS_POOL[node.battle.key]`, one `loadWorldMonster`), and `battle.count` is read **nowhere** for a node battle — its only read in the file is the `combat` bit's passthrough `@22296`, which builds a `battle` object and hands it straight back to `preBattle`. So `count:7` and `count:1` are the same fight, and `count` is documentation that looks like data. **What promises otherwise:** `TLS`'s `'Void Walker ×7 → Void Warlord'` is a two-stage escalation in prose (§DX-02gv shipped the second stage as the whole fight, which is now the honest reading of the field); `CNTR` reads `'Void Walker ×3'` with `count:3`; `RUH` reads `'Desert Wanderer ×2'` with `count:2`. Every `×N` label in the file is currently a claim the engine cannot honour.
> **Fix:** this is the engine feature §DX-02gv's option (a) needed and deliberately did not build. Two shapes: (1) **make `count` real** — the same monster N times, one `loadWorldMonster` per wave, HP carried between them, which honours every `×N` label with no data change; (2) **make the sequence real** — `battle.waves:[{key,count},…]`, which additionally honours `TLS`'s `→`, and under which `count` becomes a wave field rather than a battle field. **Recommendation: (1) first** — it is the smaller change, it retires the whole `×N` class, and (2) is a strict extension of it. Both need a call on how HP, conditions and the surprise/stealth roll carry across a wave boundary, which is why this is 🟠 and not 🟡.
> **Provenance:** §DX-02gv, on finding that the recommended fix for a mislabelled boss fight was an engine feature and filing it rather than doing it inline.

>
> 1. **`choice` has a complete contract and an empty handler.** The contract (`choice:      { required@22004`) is rigorous — requires `prompt` + `options`, validates ≥2 options each carrying a `label` and a `bits` array. It was never written because **a synchronous `for` loop cannot wait for a human being.**
> 2. **`item_check` writes a predicate nobody reads.** `ctx._itemCheck@22318` sets it; a full-file grep returns that line and nothing else. It is a conditional in a language with no `if` — it evaluates and evaporates.
> 3. **`skill_check` works only by smuggling.** It is the one bit that branches, and it does so by hardcoding the branch *inside the leaf*: `resolveSkillCheck` → `execBits(pass ? bit.onPass : bit.onFail)` (`execBits(pass ?@22266`). >
