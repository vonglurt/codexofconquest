## Standing Directive — Code Comments (user directive 2026-08-23)

> **Binding on every increment in this file.** Where this and a §-row's own instructions disagree, this wins.

**The failure this prevents:** writing a comment that narrates the change being made right now. That context is real, but it expires the instant the change merges — the defect it describes no longer exists, so the comment becomes a story about a problem no future reader can observe. It is a changelog entry in the wrong file, and a third copy of text already required in the commit body and the PR description.

- **CC-1 (MUST NOT)** Write a comment describing a change, a fix, a defect, its cause, or what the code used to do. No *"was / now / previously / instead of"*, no *"this fixes"*, no *"needed because otherwise"*, no *"note that we no longer"*.
- **CC-2 (MUST)** Apply the **survival test** to every comment before writing it: *would this still be true and useful to someone reading this file a year from now, who never saw the diff?* If it only makes sense beside the diff, it is changelog — delete it and put it in the commit body.
- **CC-3 (MUST)** Default to **zero** comments. Declarative config — Terraform, DNS records, k8s manifests, CI YAML, Helm values — is self-describing and takes none. A resource named `dmarc-example-com` does not need a comment saying it is the DMARC record.
- **CC-4 (MAY)** Comment only when a future editor would actively break something without it: a non-obvious external constraint, a required out-of-band manual step, an invariant the surrounding code cannot show. **One line.** If it needs a paragraph it belongs in a design doc, not inline.
- **CC-5 (MUST)** Before every commit, re-read the comment lines added: `git diff --cached | grep '^+' | grep -E '#|//|/\*'`. Each hit must pass CC-2 on its own. **Deleting is always an acceptable outcome.** *"I already wrote it"*, *"it is only one line"*, and *"this one is genuinely useful"* are not exemptions — the last one is the exact thought that precedes every violation.
- **CC-6 (MUST)** Applies to comments **edited** as well as added. When a change invalidates an existing comment, the default action is **DELETE**, not rewrite it into a new narrative.

> **⚠️ KNOWN TENSION, flagged not resolved — needs a user call.** This repo currently runs an *opposite* convention in `play.html`: **§AUDIT-03n / §DX-02c "annotate, don't rewrite"**, which deliberately preserves defect history inline (e.g. `const NODE_NPC_KEYS`'s 8-line comment explaining that 21 of 26 rows named retired node codes, or `_renderFinalMap`'s §AUDIT-03e note on why the node filter is held at the historical set). Those are exactly the *"what the code used to do"* narratives CC-1 forbids, and several are load-bearing: they are the only record of why a value is held where it is, and deleting them would re-open closed audit rows. **Until the call is made, the working rule is:** CC-1..CC-6 bind all **new** comments; existing §AUDIT-/§DX-annotated blocks are **not** swept under CC-6 — they are a documented archaeology convention, not accidental changelog. Filed as **§DX-02fa** below.

### §DX-02cp — `ENGINE_VER` has not moved since the commit that created it, so one leg of the mesh compatibility triple is inert (NEW 2026-08-17 during §DOC-02bv, 🟡 small design call)

- [ ] **§DX-02cp — *"every release is deliberately a separate, incompatible swarm"* is carried entirely by `worldHash`.** 🟡 **design call: bump-on-release, derive, or retire the leg.** The mesh admits a peer only on an exact `(proto, engineVer, worldHash)` match — the gate that stops a player being replicated onto a map where their cell is open ocean. `ENGINE_VER` is the middle term, parsed out of the game file by `src/js/wbapi-server.js:function getManifest@676`, and its stated job is to make each *build* its own swarm. **It has read `coc-3.104.0` since `80526b1` (2026-07-02) — the commit that introduced it — across the 4,218 lines added since**, so it has never once separated two builds. The swarm does still fork correctly, because `worldHash` covers the raw source spans of all eight data collections and changes on any data edit; the triple is doing its job through one leg while a second contributes nothing. **The consequence is narrow but real:** an engine-only change — a combat formula, a new opcode, a renamed render path — moves no data collection, so two servers running materially different *code* against identical data are judged compatible and will gossip. That is mostly harmless for display-only presence and much less so for the duel kernel, whose whole premise is *"a machine that disagrees with a pure function of committed inputs"*: replay-checking depends on both sides running the same function. **Three options, and the call is which:** (a) **bump on release** — cheapest, but it is a human step and human steps rot, which is how it got here; (b) **derive it** — hash the `DUEL:CORE`/`MOVER:CORE`/`QUEST:CORE` parity spans, which are already extracted and already byte-pinned, making the version a property of the code the way `worldHash` is a property of the data; (c) **retire the leg** and document that `worldHash` is the whole gate, which is honest but gives up on engine-level compatibility. **(b) is the one that matches the architecture** — the report's own principle is that identity is what you *are*, not what you are *called*. **Related:** `check:worlddiff` already treats an `ENGINE_VER` bump as a code-differs condition, so option (b) has a consumer waiting. **Risk:** medium — any change here re-partitions live swarms by construction, so it wants a `MESH_PROTO` bump alongside. **Verify:** the harness's incompatibility checks still pass with the new derivation, and two servers differing only in a parity module refuse each other with 409.

### §EDITOR-04 — the mission wizard: author a quest with its questline in view, and nothing else (NEW 2026-08-23, user directive, 🟠 design call on scope — increments 1–2 are 🟢)

- [ ] **The ask, in the user's words:** *"a better wizard which will query associated information so we know but are not distracted… consider the lifecycle of mission creation and editing… perhaps this is for the editor."* Today authoring a mission means holding the questline in your head. `./bin/api list quest --arc … --node … --type …`, `./bin/api get quest <id>`, `./bin/api chain <id>`, `./bin/api location <CODE>` and `./bin/api audit` each answer one question, in a terminal, one at a time — and the four traps in `resume.md §5` are all *relational*, so none of them is visible from the quest being written.
> **The four traps the wizard exists to make visible, each already measured elsewhere in this backlog.** (1) An `activateNode` that resolves but **cannot be stood on** — invisible in play, green in every gate (§DX-02w). (2) A `gate` flag with **no writer** — 55 flags, 138 unreachable quests (§AUDIT-03bj). (3) An `onComplete` that sets the flag its own `completion` waits on — 5 deadlocks, 3 of them a chain stranding 4 quests (§AUDIT-03bh). (4) A kill counter whose identity is never written (§DX-02cy, fixed) — the class, not the instance.
> **The lifecycle to model, and it is the actual deliverable.** *Locate* (which arc, which node, which NPC, what already exists there) → *Draft* (id, type, title, the four texts) → *Wire* (`activateNode`/`waypointNode`, `gate`, `onPass`/`onComplete`, `itemChain`) → *Prove* (cell primacy, gate has a writer, completion has a non-self path, `audit` errors 0) → *Place in the line* (what now precedes and follows it) → *Edit/retire* (`chain` + `canDelete` before anything is cut). Creation is the easy half; **editing an existing mission inside a live line is the half with no tool at all.**
> **Increment 1 (🟢) — the context query, server-side.** One endpoint that takes a node code or an arc and returns the whole neighbourhood in one response: quests at that node, the NPC(s) anchored there, every flag those quests read, every flag they write, which of those flags has no writer, and cell primacy for the node. Everything it needs is already parsed by `wbapi-core`; nothing new is read from the file. **This is the piece that removes the distraction** — one call instead of six, and the answer is the questline, not the quest.
> **Increment 2 (🟢) — the same thing at the CLI**, `./bin/api context <NODE|--arc X>`, so the wizard and the terminal share one implementation and the endpoint is provable without a browser.
> **Increment 3 (🟠 ASK — this is where the design call is) — the surface in `edit.html`.** A wizard pane that walks the lifecycle above, showing at each step only the slice of increment 1's response that step needs, and refusing to advance while a trap is live: no unstandable `activateNode`, no writer-less `gate`, no self-satisfying `completion`. **Open question: is it a new tab, or does it replace the Mission Builder (§EDITOR-02, shipped 2026-06-27) rather than sit beside it?** A second authoring surface that disagrees with the first is worse than either.
> **Increment 4 — drive it live.** `edit.html` in Chrome through the browser-automation tools, authoring one real mission end-to-end against a running WBAPI, is the acceptance test. Per the standing rule the acceptance is a **round trip**: create through the wizard, reload, re-read through the API, assert the quest is there and *nowhere else* changed.
> **Do not start increment 3 before 1 and 2 exist.** The distraction the user named is a data-shape problem before it is a UI problem, and a wizard built over six separate calls will inherit the six.
