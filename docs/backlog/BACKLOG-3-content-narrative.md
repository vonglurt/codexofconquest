## Standing Directive — Code Comments (user directive 2026-08-23)

> **Binding on every increment in this file.** Where this and a §-row's own instructions disagree, this wins.

**The failure this prevents:** writing a comment that narrates the change being made right now. That context is real, but it expires the instant the change merges — the defect it describes no longer exists, so the comment becomes a story about a problem no future reader can observe. It is a changelog entry in the wrong file, and a third copy of text already required in the commit body and the PR description.

- **CC-1 (MUST NOT)** Write a comment describing a change, a fix, a defect, its cause, or what the code used to do. No *"was / now / previously / instead of"*, no *"this fixes"*, no *"needed because otherwise"*, no *"note that we no longer"*.
- **CC-2 (MUST)** Apply the **survival test** to every comment before writing it: *would this still be true and useful to someone reading this file a year from now, who never saw the diff?* If it only makes sense beside the diff, it is changelog — delete it and put it in the commit body.
- **CC-3 (MUST)** Default to **zero** comments. Declarative config — Terraform, DNS records, k8s manifests, CI YAML, Helm values — is self-describing and takes none. A resource named `dmarc-example-com` does not need a comment saying it is the DMARC record.
- **CC-4 (MAY)** Comment only when a future editor would actively break something without it: a non-obvious external constraint, a required out-of-band manual step, an invariant the surrounding code cannot show. **One line.** If it needs a paragraph it belongs in a design doc, not inline.
- **CC-5 (MUST)** Before every commit, re-read the comment lines added: `git diff --cached | grep '^+' | grep -E '#|//|/\*'`. Each hit must pass CC-2 on its own. **Deleting is always an acceptable outcome.** *"I already wrote it"*, *"it is only one line"*, and *"this one is genuinely useful"* are not exemptions — the last one is the exact thought that precedes every violation.
- **CC-6 (MUST)** Applies to comments **edited** as well as added. When a change invalidates an existing comment, the default action is **DELETE**, not rewrite it into a new narrative.

> **⚠️ KNOWN TENSION, flagged not resolved — needs a user call.** This repo currently runs an *opposite* convention in `play.html`: **§AUDIT-03n / §DX-02c "annotate, don't rewrite"**, which deliberately preserves defect history inline (e.g. `const NODE_NPC_KEYS`'s 8-line comment explaining that 21 of 26 rows named retired node codes, or `_renderFinalMap`'s §AUDIT-03e note on why the node filter is held at the historical set). Those are exactly the *"what the code used to do"* narratives CC-1 forbids, and several are load-bearing: they are the only record of why a value is held where it is, and deleting them would re-open closed audit rows. **Until the call is made, the working rule is:** CC-1..CC-6 bind all **new** comments; existing §AUDIT-/§DX-annotated blocks are **not** swept under CC-6 — they are a documented archaeology convention, not accidental changelog. Filed as **§DX-02fa** below.

### §AUDIT-03bk — the arrival-completes-the-quest closure is the game's best interaction and 16 of 161 waypoint quests use it (NEW 2026-08-18 during §DOC-02ca · **the navigability half shipped 2026-09-07 `800b5ae`; the conversion half retagged 🟢 → ASK the same day, because the fix as written is wrong for the commonest shape**)

- [~] **§AUDIT-03bk — the mechanism is shipped, correct and tested; the content did not follow it.** ~~🟢 **authoring, not engineering.**~~ **ASK from 2026-09-07 — see the amendment below: the row's own fix would be wrong for the largest class of waypoint quests, and which quests should complete on arrival is an authoring rule nobody has written down.** A quest publishes a destination through `waypointNode`; `const distTag = _wpDistTag(q.waypointNode);@30907` renders **Navigate →** with a live *"(12 steps, NE)"* tag; the auto-travel loop walks the road; and if — and only if — the quest's completion gate carries the `atNode` term (`if (g.atNode && st.currentCode !== g.atNode) return false;@22147`) the final `cellMove` completes it on arrival, fires its `onComplete` bits, and may open the next quest's gate **on the same frame**. *Arriving is completing.* **Measured: 161 quests carry a `waypointNode` at HEAD, 19 quests use `completion.atNode`, and only 15 have both — 9 %.** At the 2026-07-07 build it was 12 of 150, 8 %.
> **Why it is worth a row rather than a shrug.** This is the single loop that makes a 2,853-quest world navigable without a checklist: one click, the character walks, the journal ticks over by itself. The other 146 waypoint quests send the player somewhere and then make them work out for themselves that they have arrived — the §PLAY-01 finding for this game in miniature, *the engine knows things it will not transmit*. It is also the cheapest possible content win in the repo: the engine change is **zero**, and each conversion is one `atNode` key added to an existing `completion` clause through `./api.sh`.
> **AMENDED 2026-09-07 — the census is re-derived, one half shipped, and the other half's prescription is disproved.**
>
> **The numbers moved and one of them was read wrong.** At HEAD before this increment: **161** quests carry `waypointNode` (unchanged), **23** carry `completion.atNode` (the row said 19), and **19** carry both (the row said 15 — its 15 is the count of a *shape*, not of *both*, which is the distinction the rest of this amendment is about). **12 %**, not 9 %.
>
> **`atNode` is an AND term, so it can only withhold completion — never cause it.** `` `if (g.atNode && st.currentCode !== g.atNode) return false;@22151` `` sits inside `canComplete` beside the other terms. The row's stated hazard — *"a quest that completes on arrival at a node the player passes through incidentally will fire early"* — is the one thing adding `atNode` cannot do. **The real hazard is the opposite and it is unstated: a quest whose other completion terms are satisfied away from the node can now never complete until the player walks back.** For the 80 of the 142 unconverted quests whose completion is `flags`/`flagsPath`, that is a softlock risk per conversion, not a free win.
>
> **And the fix as written conflates two different fields.** The row's remedy is *"add `atNode:'X'` to their completion gate"* where X is the waypoint. Measured over the 19 that already have both: **15 are `atNode == waypointNode`** — go there and it is done — and **4 are `atNode == activateNode ≠ waypointNode`**: `quest_fishing_guide` (fish at `BOO`, **return to the Fisherman at `SSJ`**), `quest_brynn_ledger` (`BMA` → back to `TLL`), `quest_couperin_lute` (`LLA` → back to `MHQ`), `quest_pachelbel_shipment` (`KRN` → back to `LLA`). **`waypointNode` is where to go next; `atNode` is where completion happens, and for a fetch-and-return quest those are different by design.** Applying the row's rule to that class would demand the player finish the quest at the place they fetch from, which is the opposite of what its own `hint` says — *"Cast your line at Yugurt Lake at least once, **then return to the Fisherman**."*
>
> **What shipped, because it is decidable and additive.** The inverse direction of the same argument has no softlock risk at all: a quest that requires arrival somewhere should *say* where. `check:questgraph` gains an arrival-route census — every `completion.atNode` quest is **go-there** (`atNode == waypointNode`), **routed another way** (a waypoint, or `atNode == activateNode`, so the player walks back or never left), or **unrouted**. **Red at HEAD with exactly one:** `quest_sea_01` — *"Sail east from the Tilbury Star into the open water"* — completes only at `NWI`, is given at `SEN`, and published no `waypointNode`, so the Navigate button never appeared for the one quest whose entire completion condition is going there. `NWI` is `{r:17,c:181}` and `SEN` `{r:18,c:180}`, both off every `SEA_RUNS` range, so the two-step path exists. Fixed through `./bin/api put quest quest_sea_01 waypointNode=NWI`, round-tripped from disk. **go-there 15 → 16 · unrouted 1 → 0.**
>
> **What is left, and why it is now ASK.** The 142 unconverted waypoint quests are **not** one class: 28 complete on `battles` (the row already excludes them), 80 on `flags`/`flagsPath`, 16 on `countMin`, 9 on `items`, 6 on nothing at all. **106 of the 142 have prose naming the waypoint's place**, so the row's *"the ones whose `hint` already says go to X"* filter selects almost the whole set and does not discriminate. **The question the author has to answer is which of the two shapes each quest is** — go-there, or fetch-and-return — because the answer decides whether `atNode` is the waypoint or the giver, and getting it backwards makes the quest uncompletable rather than merely unimproved. **Recommended:** (a) a rule the corpus can be sorted by — *a quest whose `passText` describes the giver reacting completes at the giver; one whose `passText` describes the destination completes at the destination* — applied in one batch through `./bin/api` with the classification recorded per quest, exactly the §AUDIT-03b method; (b) convert only the `items`/`countMin` set (25), where arrival with the thing in hand is unambiguous; (c) leave it and keep the census as a health number. **(a) is recommended**, and it needs the author to ratify the rule before 142 quests are sorted by it.
> **Fix:** audit the 146 for the ones whose `hint` already says *"go to X"* and add `atNode:'X'` to their completion gate; leave alone the ones whose waypoint is a *battle* destination (the Battle button path) or a multi-stop errand. **Do not blanket-apply** — a quest that completes on arrival at a node the player passes through incidentally will fire early, which is the failure mode `atNode` exists to prevent in the other direction. **Verify:** a Playwright pin per converted quest, the §MATH-01 shape (activate at A, hold at B, complete at C); `check:questgraph` unchanged.
